## High-confidence candidates

### [Fixed] C1. Subject reword silently deletes `#`-prefixed body lines

- **Severity:** High (silent user-data loss; contradicts documented behavior)
- **Confidence:** High — empirically reproduced (V2)
- **Affected:** `extension.js:338–343` (`getCommitMessage`), `extension.js:154–164` (reword loop), `extension.js:355–366` (`runHistoryReword`); `README.md:22` ("A message body is preserved when only its subject is edited")
- **Description:** The reword flow reconstructs the full message (`joinMessage(newSubject, tail)`) and delivers it through a `GIT_EDITOR` that copies the file over git's buffer. `git history reword` applies default commit cleanup when accepting the edited message: lines beginning with the comment char (`#` by default; `core.commentChar` dependent) are stripped.
- **Why it matters:** Commits whose bodies legitimately contain `#` lines (issue refs like `#123`, commented notes, scripts) lose those lines permanently on any subject edit. The extension's core promise — only the subject changes — is violated silently; no error, no backup diff surfaced beyond the ref backup.
- **Evidence:** Test repo commit stored message `"second commit\n\n# ticket 123\nbody with trailing ws\n\nend\n"`; after running the extension's exact mechanism: `"SECOND COMMIT (edited)\n\nbody with trailing ws\n\nend\n"` — the `# ticket 123` line is gone (V2).
- **Expected impact:** Permanent deletion of body content for any affected commit; users unaware until much later.
- **Conditions:** Subject edit on a commit whose body contains one or more `#`-prefixed lines (or, secondarily, other default-cleanup mutations such as whitespace stripping for plumbing-created messages).
- **Suggested verification/fix direction:** Pass the message with comment cleanup disabled (e.g. `-c core.commentChar=…` override, `--cleanup=verbatim` equivalent if `git history reword` supports it, or a comment-char git can't match) and re-run V2; add a regression test with `#` bodies.

#### Update — 2026-09-09 22:23 — Base 6bc5923

Reproduced the loss using the installed `git history reword` flow. `commit.cleanup=verbatim` did not prevent cleanup, and `core.commentChar=auto` still removed `#` lines. The reword invocation now uses the escaped control comment character `\001`, avoiding collisions with printable body content. A regression test exercises the actual command and preserves `#`, `?`, `;`, backslash, and control-prefixed lines (`node --test test/c1-comment-body.test.js test/c2-byte-fidelity.test.js test/c3-extended-header.test.js`). Fixed.

### [Fixed] C2. Non-UTF-8 commit messages are permanently corrupted (U+FFFD) by both reword and timestamp rewrite

- **Severity:** High (silent irreversible data corruption)
- **Confidence:** High — empirically reproduced end-to-end (V3)
- **Affected:** `extension.js:382–407` (`git()` — `execFile` resolves stdout as UTF-8 string), `extension.js:338–343` (`getCommitMessage`), `extension.js:268` + `247` (message round-trip through `getCommitMetadata` → `commit-tree` stdin), `extension.js:359` (utf8 message file write)
- **Description:** Commit objects are raw byte strings; legacy repositories commonly contain Latin-1/other non-UTF-8 messages (SVN imports, old Windows repos). The extension decodes `cat-file commit` output as UTF-8, so every undecodable byte becomes U+FFFD in the JS string; that replacement character is then written back (message file for reword, stdin for `commit-tree`), permanently replacing the original bytes in the rewritten commits.
- **Evidence:** Legacy commit with message bytes `…caf e9 … accents: e9 e8` (hex `636166e9…e9e8`) → `getCommitMessage` returned `"caf\ufffd … \ufffd\ufffd"` → after reword, stored bytes are `efbfbd efbfbd` (UTF-8 U+FFFD); git accepted it without any error (V3). The `encoding ISO-8859-1` header was also dropped (C3).
- **Why it matters:** A single Sync silently destroys message content across every rewritten commit in such repos; the damage is baked into object history and spreads on push.
- **Conditions:** Any commit in the rewritten range whose message contains bytes invalid in UTF-8. Subject-only edits, timestamp-only edits, and pass-through commits during `rewriteDates` are all affected (all paths round-trip the message through a JS UTF-8 string).
- **Suggested verification/fix direction:** Round-trip raw bytes: use Buffers (`encoding: 'buffer'`) for `cat-file`/`commit-tree` paths; re-run V3 and diff stored hex before/after.

#### Update — 2026-09-09 21:59 — Base 95014c4

Verified with disposable repositories containing invalid UTF-8 message bytes. `cat-file` output had been decoded as UTF-8 before the reword and timestamp-rewrite paths, replacing invalid bytes with U+FFFD. Commit messages now remain Buffers through extraction, message-file writes, and `commit-tree` stdin; only a newly entered subject is UTF-8 encoded before being joined to the raw tail. Added Node regression coverage for timestamp rewriting and subject rewording; both preserve the expected raw bytes (`node --test test/c2-byte-fidelity.test.js`). Fixed.

### [Fixed] C3. Timestamp rewrite drops `encoding`, `gpgsig`, and `mergetag` headers from every rebuilt commit

- **Severity:** Medium-High (silent loss of signatures/encoding declarations across the rewritten suffix)
- **Confidence:** High — header drop empirically confirmed for `encoding` (V4); structural for `gpgsig`/`mergetag` (the rebuild writes only tree/parent/author/committer + message; `commit-tree` has no mechanism to carry them)
- **Affected:** `extension.js:220–252` (`rewriteDates` commit-tree rebuild), `extension.js:257–284` (`getCommitMetadata`, which discards all headers except identity/date/tree/parents)
- **Description:** `rewriteDates` rebuilds the affected linear suffix commit-by-commit with `git commit-tree`. Signed commits (GPG/SSH/X.509) lose `gpgsig`; commits from migrated/imported histories lose `encoding` and `mergetag`. This applies not only to the commits the user edited but to **every** commit in the suffix (all descendants of the oldest edited commit), even those whose timestamps are unchanged.
- **Evidence:** Raw commit with `encoding ISO-8859-1` header rebuilt through the extension's exact `getCommitMetadata`+`commit-tree` flow: rebuilt object lacks the header and has a different hash (V4). Combined with C2, the message bytes are simultaneously corrupted.
- **Expected impact:** Failed `git verify-commit` after sync; altered display of legacy-encoded messages; signed-commit guarantees silently voided for the whole suffix.
- **Conditions:** Any Sync containing at least one timestamp edit where the affected suffix contains signed/legacy-encoded/tag-merged commits.
- **Suggested verification/fix direction:** Detect `gpgsig`/`encoding`/`mergetag` via `cat-file commit` header scan before rewriting and abort with a targeted error (simplest), or re-sign with `-S`; keep C2's byte-fidelity fix in the same pass.

#### Update — 2026-09-09 22:06 — Base 219e63c

Verified that a timestamp rewrite rebuilt a disposable commit with `encoding ISO-8859-1` but omitted that header. `commit-tree` cannot retain extended commit headers. Timestamp rewriting now scans every affected raw commit header before creating any replacement object and rejects `encoding`, `mergetag`, and `gpgsig*` headers with the affected commit ID. Added a regression test confirming rejection occurs before the branch changes (`node --test test/c2-byte-fidelity.test.js test/c3-extended-header.test.js`). Fixed.

### [Fixed] C4. Edits typed during a running Sync are silently discarded

- **Severity:** Medium (silent loss of user input; confusing state)
- **Confidence:** High — direct webview code path
- **Affected:** `extension.js:569–575` (sync click disables only the two buttons), `extension.js:593–601` (`syncDone` handler), `extension.js:506–538` (`render()` rebuild)

- **Conditions:** User types into any row while a Sync is in flight (likely precisely because the panel is visible and busy for seconds).

### [Fixed] C5. N+1 subprocess storm: up to ~4 git spawns per affected commit, twice per Sync

- **Severity:** Medium (perceived hang, extension-host load, wasted work)
- **Confidence:** High — pure code fact; impact estimated from measured Windows spawn cost
- **Affected:** `extension.js:257–284` (`getCommitMetadata` runs `git show -s` **and** `git cat-file commit` per commit), called from `extension.js:185–195` (`assertLinearAffectedHistory`) and again from `extension.js:203–209` (`rewriteDates`)
- **Description:** A single timestamp edit at ordinal ~199 (the oldest row the UI shows) triggers: 1 `rev-list` + 200×2 spawns in `assertLinearAffectedHistory` (which fetches full commit messages it never uses), then 1 `rev-list` + 200×2 spawns again inside `rewriteDates`, plus one `commit-tree` per commit. That is ~800 process spawns before the 200 `commit-tree` calls. At typical Windows `execFile` overhead (tens of ms each) this is tens of seconds with only a static "Rewriting commit timestamps…" status, inside the extension host.
- **Why it matters:** Users will read this as a hang; the linearity pass can be one batched `git log` (parents only), and messages are only needed for the `commit-tree` pass. `assertLinearAffectedHistory`'s message fetch is pure waste.
- **Conditions:** Edits far from HEAD; any Sync on slower machines.

- **Suggested verification/fix direction:** Batch with a single `git log --first-parent --format=…` call per pass; reuse one metadata pass for both the linearity check and the rebuild; measure wall time at index 199 before/after.

### [Fixed] C7. Rollback report can be false: rollback failure is swallowed, success is asserted unconditionally

- **Severity:** Low (diagnostic integrity during worst-case failures)
- **Confidence:** High — unconditional message composition
- **Affected:** `extension.js:171–174`
- **Description:** The catch block runs `update-ref … headRef currentHead` with `.catch(() => {})`, then always appends `(Sync rolled back to <hash>.)` to the user-facing error. ## Plausible candidates

### [Fixed] P1. TOCTOU: commits made mid-Sync shift ordinals; later rewords hit the wrong commits

- **Severity:** Medium (wrong-commit message application; rollback still restores the branch tip)
- **Confidence:** Plausible — mechanism concrete, window real, likelihood environment-dependent
- **Affected:** `extension.js:120–123` (one-shot `baseHead` staleness check), `extension.js:156–164` (loop uses live `HEAD~<index>` ordinals across multiple rewords), `extension.js:247–254`
- **Description:** The staleness guard compares `HEAD` to `baseHead` once, before any rewriting. Each iteration then resolves `HEAD~<index>` against the *live* HEAD. The loop is long (one `git history reword` per subject change, each spawning the editor helper), so an external `git commit` (terminal, another tool, auto-fetch fast-forward… note: ff would also change HEAD) between iterations shifts every subsequent ordinal by one — the remaining prepared messages are applied to the wrong logical commits. No lock (index lock, ref transaction, or `GIT_INDEX_FILE` isolation) is held across the loop.
- **Conditions:** Concurrent commit/branch update landing inside the sync window; more likely with many changes (longer window) and active background tooling.
- **Suggested verification/fix direction:** Pin the range up front: resolve all target hashes from the verified `baseHead` (e.g., `baseHead~<index>`) instead of live `HEAD~<index>`, and/or re-check `rev-parse HEAD` before each reword; abort on drift.

#### Update — 2026-09-09 22:59 — Base f044cc0

Verified that later subject-message reads used live `HEAD~<index>` ordinals after the initial staleness check. Sync now pins original target hashes from the verified head, reads the intended original messages by hash, and checks for intervening HEAD movement between rewrite stages before proceeding. Mocked and disposable-repository regression coverage verifies stable targets, drift detection, and ordinary linear rewrites (`node --test test/p1-target-pinning.test.js`). Fixed.

### [ ] P2. `git` binary resolved only from PATH; ignores VS Code `git.path` setting and the built-in extension's resolution

- **Severity:** Medium (total failure on affected setups)
- **Confidence:** Plausible — mechanism certain (`extension.js:384–391` hard-codes `'git'`), trigger depends on environment
- **Affected:** `extension.js:382–407` (`cp.execFile('git', …)`), contrast `extension.js:304–325` (uses `vscode.git` API for repositories but not for the git path)
- **Description:** The extension discovers repositories through the built-in Git extension but spawns `git` by bare name. Users where git is not on the extension-host PATH (common on Windows with portable git registered only via `git.path`) get `spawn git ENOENT`-style errors for every operation, while built-in Git works fine — an inconsistency that is hard for users to diagnose.
- **Conditions:** Git reachable only through the `git.path` setting (or PATH differences between terminals and the extension host).
- **Suggested verification/fix direction:** Read `git.path` configuration and/or `vscode.git` API's git path; fall back to PATH. Verify by launching VS Code with git only available at a custom path.

### [ ] P3. Race: rapid double invocation creates two panels for the same repository

- **Severity:** Low
- **Confidence:** Plausible — concrete async gap
- **Affected:** `extension.js:21–45` (`await pickRepository()` and `await assertGitHistorySupported()` occur *before* `panels.get`/`panels.set`, and `panels.set` happens after `createWebviewPanel`)
- **Description:** Two near-simultaneous command invocations (e.g., double-click on the SCM title button) both pass the `panels.get(cwd)` miss (their awaits interleave), both create panels; `panels` retains only the second. Two live webviews for one repo can then run Syncs concurrently against the same `baseHead`; the second Sync fails the staleness check after the first completes (safe), but the orphaned panel is never revealed again by the command and the map/panel relationship is inconsistent.
- **Conditions:** Two invocations within the pick/version-check await window (ms), single-repo workspaces (no QuickPick pause).
- **Suggested verification/fix direction:** Register a sentinel in `panels` synchronously at command start, or key on the resolved repository before the first await.

### [ ] P4. Backup refs accumulate without bound; no prune/cleanup path

- **Severity:** Low-Medium over time
- **Confidence:** Plausible — behavior certain, impact gradual
- **Affected:** `extension.js:286–302` (`createBackupRef`); no corresponding deletion anywhere; README advertises the refs but not their lifecycle
- **Description:** Every Sync creates `refs/git-history-reword/backup-<local-timestamp>` and keeps the entire pre-rewrite history reachable forever. There is no command, cap, or expiry. Heavy users accumulate hundreds of refs; `git show-ref`/IDE ref listings grow, and rewritten-away object graphs are never garbage-collected.
- **Conditions:** Long-term routine use.
- **Suggested verification/fix direction:** Add a retention policy (e.g., keep last N, delete on explicit command) and document it; consider `git for-each-ref refs/git-history-reword` count on a long-lived test profile.

## Investigation leads

### [ ] L1. Unbounded `change.index` from webview messages can drive an unbounded spawn loop

- **Severity:** Low (hardening; message source is the extension's own webview)
- **Confidence:** Lead — path concrete, no benign trigger
- **Affected:** `extension.js:133` (only `index >= 0` is validated), `extension.js:185–195` + `257–261` (`getCommitMetadata(count)` loops over `count` commits with 2 spawns each; `rev-list --max-count=<count>` itself is unbounded)
- **Description:** A crafted/replayed `sync` message with `index: 999999` makes `assertLinearAffectedHistory` fetch up to `maxIndex+1` commits before its guard `records.length <= maxIndex` can reject — potentially hundreds of thousands of subprocess spawns on a large repo (effectively an extension-host freeze). Also reachable if UI/model indexes ever desync.
- **Suggested verification/fix direction:** Clamp `index` to `model.commits.length - 1` server-side (the extension knows the list it sent); fail fast before any spawn.

### [ ] L2. Count/trim asymmetries: spurious dirty rows, "Synced N commits" overcounts

- **Severity:** Low (cosmetic/diagnostic)
- **Confidence:** Lead — logic traceable, edge-triggered
- **Affected:** `extension.js:540–545` (webview compares trimmed input vs. untrimmed original → row dirties when only whitespace differs), `extension.js:157` (backend skips whitespace-only changes), `extension.js:180` (success count = `normalized.length` regardless of skipped rewords)
- **Description:** Subjects stored with leading/trailing whitespace (plumbing-created commits) mark rows dirty without user action; Sync then reports "Synced 1 commit" while performing zero rewrites. Misleading progress reporting erodes trust in the tool's feedback.
- **Suggested verification/fix direction:** Count actually-applied rewords; compare against normalized originals on both sides.

### [ ] L3. Vestigial duplicate command and committed build artifact

- **Severity:** Low (maintainability)
- **Confidence:** Lead
- **Affected:** `package.json:27–31` (`gitHistoryReword.reword` — identical behavior to `open`, no menu/keybinding ever targets it), `git-history-reword-ver2.vsix` (build output committed to source control; currently byte-identical to source per V11, but guaranteed to drift on the next edit)
- **Suggested verification/fix direction:** Remove the duplicate command or give it a distinct purpose; drop the .vsix from version control (`.vscodeignore` already excludes it from packaging).

## Checked and cleared (no finding)

These suspected issues were investigated and rejected, recorded to prevent re-litigation:

- **Ordinal stability of the oldest-first reword loop** (`HEAD~<index>` across successive rewrites): sound for linear history; merge commits inside or across the affected range are correctly rejected by `assertLinearAffectedHistory` (both directions: newer-than-merge edits are safe; through-merge edits are blocked).
- **`\x1e`/`\x1f` record parsing of `git log` output** incl. per-record newline stripping, empty-parent, and multi-parent records: verified against real git output (V6).
- **`getCommitMessage` first-`\n\n` separator** vs. multi-line headers (gpgsig continuation lines start with a space): safe.
- **Dirty worktree / staged index during `git history reword`**: works; staged entries survive (V5).
- **Detached-HEAD subject-only Sync**: `git history reword` moves HEAD; `symbolic-ref` fallback to `'HEAD'` (extension.js:149) makes both rollback paths (`update-ref HEAD`) valid; timestamp path correctly refuses detached HEAD *after* the subject phase — combined with rollback this is recoverable, though doing half the work before failing is worth a pre-check during the fix phase.
- **Branches other than the current one pointing into rewritten history**: not moved by `--update-refs=head` (V10) — rebase-like divergence, and consistently outside the rollback's (correct) scope. No defect, but worth a UX hint in the fix phase.
- **`commit-tree` message normalization** (trailing-newline concerns): verbatim preservation verified (V9).
- **Webview date round-trip** (DST-correct offsets, sub-second truncation, cleared-input handling, ISO acceptance by `GIT_AUTHOR_DATE`/`GIT_COMMITTER_DATE`): verified logically and via V8.
- **`child.stdin.end(options.input)` on spawn failure**: streams exist even on ENOENT in current Node; no masking of the real error.
- **XSS via commit subjects/branch/repo names**: all injected via `escapeHtml` or `textContent`; CSP is nonce-based with `script-src 'nonce-…'`.
- **`util.promisify(execFile)` object-return pitfall**: not present — the extension's `git()` uses the callback form and resolves `stdout` directly (the pitfall was reproduced only in my first test harness).

## Suggested fix-phase ordering

1. C2 + C3 (byte fidelity / header preservation — same code path, irreversible damage) — with C1 (cleanup bypass) as one "message fidelity" change-set plus regression tests built from the V1–V4 harnesses.
2. C4 + C5 (UI state + batching) — user-visible reliability of the sync flow.
3. P1 (ordinal pinning) and C7 (rollback truthfulness) — transactional integrity.
4. C6, P2, P3, P4, L1–L3 — hardening and hygiene.
